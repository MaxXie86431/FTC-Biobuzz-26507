# Keep Panels, but fix its silent bug

Panels is still the right dashboard for team 26507 in the 2026-27 BIOBUZZ season, but not at version 1.0.13. The team's build pairs `com.bylazar:fullpanels:1.0.13` with Sloth 0.3.2, and multiple teams reported that this exact combination makes `@Configurable` edits silently do nothing. Sloth reaches the classpath three ways: Pedro's `tuning` module, NextFTC v2's `robot` module, and an explicit dependency. Panels fixed the bug in **1.0.16 (2026-10-03)**, and **1.0.18 (2026-10-07)** is the current release. FTC Dashboard is not a better fit for this stack. Its last release (v0.6.0, May 2026) predates FTC SDK 12, it ships no BIOBUZZ field image, it faces the same open question about Sloth's class loading, and Pedro Pathing 3 has dropped both dashboards in favor of its own AutoTune page. AdvantageScope and the FTC file loggers add to Panels rather than replace it, because none of them can edit values live. The bigger change this season is rule **R704.D**, which names both FTC Dashboard and FTControl Panels as prohibited services. Whichever dashboard the team uses is therefore a practice-field tool, and data from real matches has to come from on-robot logs that the team reviews afterward. The recommendation has five parts. Upgrade to 1.0.18 now. Prove on the robot that edits take effect. Ship a competition build with no Panels code in it. Ask the official Q&A how far R704.D reaches. Add a small file logger once that answer arrives.

## Version 1.0.13 silently drops this team's tuning edits

The failure hit this team's stack directly. On 2026-09-22 a user opened Panels issue #19 to report that setting `@Configurable` values had no effect on SDK 12.0, although the same setup had worked on SDK 11.2.1. Several teams confirmed it. A community member traced the cause to Sloth: Pedro's tuning module bundles it, and Sloth loads a second copy of every class. Panels then edits one set of static fields while the OpModes read the other, and nothing reports an error. The maintainer closed the issue on 2026-10-03 after merging Oscar Chevalier's Sloth support ([Issue #19](https://github.com/ftcontrol/ftcontrol-panels/issues/19)). The same conflict was filed against Pedro, where a contributor asked for it to be documented prominently because the failure is silent ([PedroPathing #188](https://github.com/Pedro-Pathing/PedroPathing/issues/188)). The Pedro maintainer's reply in that thread was to switch to the "Sloth Panels" fork. That advice predates the fix: the official Prerequisites page now tells users to move from the `com.bylazar.sloth:*` artifacts back to the official `com.bylazar:*` ones, which support Sloth directly ([Prerequisites](https://github.com/ftcontrol/ftcontrol-panels/blob/main/library/Docs/web/src/docs/Prerequisites.svelte)). Configurables 1.0.7 added the Sloth-aware scanning behind the fix ([Configurables changelog](https://github.com/ftcontrol/ftcontrol-panels/blob/main/library/Configurables/web/config.ts)).

**Team 26507 is fully exposed.** In `build.dependencies.gradle`, Sloth 0.3.2 is declared explicitly, with a comment saying NextFTC's `RobotController` exposes Sloth types. `com.pedropathing:tuning:1.0.0` pulls in Sloth 0.3.0 at runtime ([tuning-1.0.0.pom](https://repo1.maven.org/maven2/com/pedropathing/tuning/1.0.0/tuning-1.0.0.pom)), and `dev.nextftc.v2:robot:0.2.1` pulls in Sloth 0.3.2 ([robot-0.2.1.pom](https://repo1.maven.org/maven2/dev/nextftc/v2/robot/0.2.1/robot-0.2.1.pom)). This rules out the interim workaround from issue #19, which was to comment out Pedro tuning: NextFTC v2 would keep Sloth on the classpath anyway. Any edits the team made in the browser to `Intake.intakeValue`, `Intermediate.intermediateValue` or the starting poses in `Poses.java` may never have reached the running OpMode. No public report covers NextFTC v2 and Panels together, so the fix is documented for Pedro's Sloth path but still needs to be confirmed on this team's robot.

1.0.13 also shipped with a second defect. It was the first release with BIOBUZZ field images, yet the Field widget did not show up. That was fixed in 1.0.14 by restoring the packaged web assets ([Issue #18](https://github.com/ftcontrol/ftcontrol-panels/issues/18); [FullPanels changelog](https://github.com/ftcontrol/ftcontrol-panels/blob/main/library/FullPanels/web/config.ts)).

The upgrade is cheap but has three catches. FullPanels 1.0.16 and later require **FTC SDK 12.0.0 and the Dairy Maven repository**, and the team already has both. The docs ask for a clean build so stale Panels web assets are not reused. They also say Kotlin consumers need **kotlin-gradle-plugin 2.4.10 or newer** ([FullPanels changelog](https://github.com/ftcontrol/ftcontrol-panels/blob/main/library/FullPanels/web/config.ts); [Prerequisites](https://github.com/ftcontrol/ftcontrol-panels/blob/main/library/Docs/web/src/docs/Prerequisites.svelte)). The team's root `build.gradle` pins KGP 2.2.10, and TeamCode applies `org.jetbrains.kotlin.android` even though it contains no `.kt` files. The metadata check may therefore never fire, but bumping to 2.4.10 (2.4.21 is the newest stable release, per [Maven Central](https://repo1.maven.org/maven2/org/jetbrains/kotlin/kotlin-gradle-plugin/maven-metadata.xml)) is the documented path. The last catch is the Android Gradle Plugin. Panels' own quickstarts build on AGP 8.7.0 ([Panels-Quickstart-Java](https://github.com/ftcontrol/Panels-Quickstart-Java)), and the team is on AGP 9.3.3, a combination nobody has documented. The 1.0.18 build needs to be verified locally. The new class-based `refreshClass` API does not matter here, because a grep of TeamCode finds no refresh calls.

Panels' maintenance record argues for caution, not for leaving. The project is effectively a **one-person effort**: Lazar has 429 commits and Oscar Chevalier has 21 ([contributors](https://github.com/ftcontrol/ftcontrol-panels/graphs/contributors)). FullPanels shipped nothing between 2025-12-12 and 2026-09-13, and the Sloth pull request sat for about nine months before the BIOBUZZ breakage forced a merge ([PR #15](https://github.com/ftcontrol/ftcontrol-panels/pull/15)). The project has now broken at the start of two consecutive seasons: the DECODE field view in November 2025 ([Issue #9](https://github.com/ftcontrol/ftcontrol-panels/issues/9)), then the BIOBUZZ field, SDK 12 and Sloth problems in September 2026. Both times the fixes arrived weeks into the season. The license is a custom non-commercial license rather than MIT, which does not restrict an FTC team ([LICENSE.md](https://github.com/ftcontrol/ftcontrol-panels/blob/main/LICENSE.md)).

## FTC Dashboard would swap a fixed problem for unverified ones

Moving to FTC Dashboard would take about an hour, but it would not lower the team's risk. Its latest release, **v0.6.0, came out on 16 May 2026**, and its last explicit SDK update targeted SDK v11 in December 2025 ([releases](https://github.com/acmerobotics/ftc-dashboard/releases); [commits](https://github.com/acmerobotics/ftc-dashboard/commits/master)). No commit mentions SDK 12 or a BIOBUZZ field image, and 21 community pull requests are waiting for maintainer Ryan Brott to merge them, including a loop-time view and record/replay ([open PRs](https://github.com/acmerobotics/ftc-dashboard/pulls)). The 0.6.0 POM compiles against SDK 10.0.0 artifacts, which Gradle will resolve up to 12.0.0 ([dashboard-0.6.0.pom](https://acmerobotics.z13.web.core.windows.net/com/acmerobotics/dashboard/dashboard/0.6.0/dashboard-0.6.0.pom)). It probably runs, but nobody has published a hardware report on SDK 12. Sloth is the larger concern. Dairy's documented route for Sloth users is a separate fork, `com.acmerobotics.slothboard:dashboard:0.3.2+0.6.0` ([Sloth README](https://github.com/Dairy-Foundation/Sloth)), and Pedro's own quickstart used Slothboard for a time while Pedro 3 was in development ([Quickstart @199aa01](https://raw.githubusercontent.com/Pedro-Pathing/Quickstart/199aa01/build.dependencies.gradle)). Switching would replace a Sloth fix that now lives upstream in Panels with one that depends on a fork. Nothing documents whether vanilla FTC Dashboard suffers the same duplicate-class problem.

Running both dashboards during a transition carries risk too. Mona Shores, a different team whose repo also takes the season's name, reported a Robot Controller crash loop on `BindException` at boot with both dashboards and Pedro 3 installed. It reproduced even with no team code in the APK, and removing either dashboard fixed it ([Mona Shores issue #69](https://github.com/Mona-Shores-FTC-Robotics/biobuzz/issues/69); [PR #70](https://github.com/Mona-Shores-FTC-Robotics/biobuzz/pull/70)). BrainStem's starter kit, by contrast, runs both on SDK 11.2.1 using the Sloth variants ([BrainStem kit](https://github.com/BrainStem-FIRST/FTC-Starter-Kit-2026)), so the conflict may depend on the specific versions installed.

Neither library pulls the team toward a dashboard anymore. **Pedro 3's quickstart ships neither dashboard.** It relies on the robot-hosted AutoTune page, and the old "Choosing a Dashboard" docs page now returns 404 ([Pedro Quickstart](https://github.com/Pedro-Pathing/Quickstart/blob/master/build.dependencies.gradle); [Pedro Tuning docs](https://pedropathing.com/docs/pathing/tuning)). That old page said FTC Dashboard could not live-tune Pedro's constants, while Panels was fully supported ([Pedro docs, Nov 2025 version](https://raw.githubusercontent.com/Pedro-Pathing/Docs/ca0f2017ba757ea761a455384506d49e6e89bd43/content/docs/pathing/dashboard.mdx)). NextFTC v2's telemetry page uses FTC Dashboard as its example backend and documents FateWeaver logging, but its `Telemetry` abstraction works with any backend, and Panels goes unmentioned ([NextFTC telemetry docs](https://github.com/NextFTC/NextFTC-Docs/blob/main/src/content/docs/robot/telemetry.mdx)).

Adoption data from a scan of 358 public FTC repos created this season and mentioning BIOBUZZ puts **Panels at 27%, FTC Dashboard at 21%, and neither at 59%** ([repo search](https://api.github.com/search/repositories?q=biobuzz+created:%3E2026-07-01+fork:true)). Panels' share was mostly inherited from old defaults. Among repos still on Pedro 2, 93% declare Panels. Among fresh Pedro 3 quickstart forks the figure is 17%, and 76% of those forks use neither dashboard ([Pedro Quickstart forks](https://github.com/Pedro-Pathing/Quickstart/forks)). Among teams that do add a dashboard on top of Pedro 3 or NextFTC, Panels is still the more common choice: 55 versus 33 repos for Pedro 3, and 11 versus 7 for NextFTC. Because the migration is so small (three annotations and two Gradle lines), the team is not locked into Panels, and FTC Dashboard works as a fallback.

## R704.D turns every dashboard into a practice-field tool

The 2026-27 Competition Manual (TU04), in rule R704.D, says robot control data, debugging data and telemetry may stream only through the FTC Driver Station app. It also states that third-party logging and streaming services, "such as FTC Dashboard, FTControl Panels, and others are prohibited." R704.C separately requires every laptop to be disconnected from the robot Wi-Fi during matches ([2026-27 Competition Manual](https://ftc-resources.firstinspires.org/ftc/game/manual)). This is new this season. Last season's R706 limited streaming but named no tools ([2025-26 manual archive](https://ftc-resources.firstinspires.org/ftc/archive/2026/game/manual)), and the BIOBUZZ wording has been in the manual since the V1 kickoff release ([firsthub.dev kickoff summary](https://www.firsthub.dev/blog/biobuzz-kickoff-ftc-2026-2027)). Since the rule names Panels and FTC Dashboard alike, it favors neither. It does shrink what the dashboard decision affects: the choice now matters only in the team's shop and on practice fields.

Three questions remain open. R704.C is limited to match play, but R704.D carries no such limit, so a strict reading could also cover streaming in the pits. The rule does not say whether a dashboard library that is installed but idle counts as a "hosted" service. And because the rule names "logging" services, it may also reach on-robot file loggers, even though those never transmit anything. No official Q&A answer on any of these was found. Pedro's AutoTune page raises the same question, since it is also a third-party web page served from the robot ([Pedro Tuning docs](https://pedropathing.com/docs/pathing/tuning)). FTC Dashboard handles events with an "Enable/Disable Dashboard" OpMode ([FtcDashboard.java](https://raw.githubusercontent.com/acmerobotics/ftc-dashboard/master/FtcDashboard/src/main/java/com/acmerobotics/dashboard/FtcDashboard.java)). No equivalent switch for Panels was found.

This team has a cheap, conservative option because it uses Panels only through annotations. If a Gradle property switches the `fullpanels` dependency from `implementation` to `compileOnly` for event builds, the three `@Configurable` annotations still compile, but the Panels runtime and its web server never reach the APK. The Android runtime ignores annotations whose classes are missing. This is an engineering inference rather than a documented Panels feature, so confirm it by booting the event build and checking that `192.168.43.1:8001` does not respond. Sloth itself streams nothing and can stay. Removing Pedro tuning from event builds would take more work, because `pedro/Tuning.java` and the `pedro/procedures` classes import it. The simpler policy is to not run tuning OpModes at events until the Q&A answers.

## Match data now has to come from files pulled off the robot

With live streaming banned at events, the only way to see what happened during a real match is to log it to storage on the robot and review the file afterward. **AdvantageScope** is the strongest viewer available to FTC. v26.0.2 (April 2026) supports FTC fields, robot models, Road Runner logs, and a live source that speaks FTC Dashboard's protocol. Its developers call the FTC support experimental and say official FTC support arrives with Systemcore in 2027-28 ([What's New in 2026](https://docs.advantagescope.org/whats-new/); [releases](https://github.com/Mechanical-Advantage/AdvantageScope/releases)). It has no Panels live source, and it does not log anything itself ([Live Sources](https://docs.advantagescope.org/overview/live-sources/)).

The FTC loggers that feed it are all young projects run by a single student or mentor. **FateWeaver** writes one `.fate` file per OpMode, publishes to Maven Central, and serves a download page from the robot. Its live `FlightProjector` stream has to be turned off for competition ([FateWeaver](https://github.com/HermesFTC/FateWeaver)). For this team it has the best integration story, because NextFTC v2 documents it and ships a dedicated Extensions module ([NextFTC telemetry docs](https://github.com/NextFTC/NextFTC-Docs/blob/main/src/content/docs/robot/telemetry.mdx); [NextFTC Extensions](https://github.com/NextFTC/Extensions)). Its README, however, says it needs an AdvantageScope build with FateWeaver v3 support. **KoalaLog** writes standard `.wpilog` files using an `@AutoLog` annotation processor and ships an ADB log puller, but it has no tagged releases and is still asking for testers ([KoalaLog](https://github.com/ori-coval/Koala-Log)). PsiKit lists both log-file review and live tuning as unsupported ([PsiKit](https://github.com/psilynx/PsiKit/)), and TRACE describes itself as a scaffold that has not been tested on hardware ([TRACE](https://github.com/The-Allsparks/TRACE)). Mona Shores avoided these dependencies by writing its own dependency-free WPILOG writer. That work exposed two pitfalls: AdvantageScope v27 requires poses in struct form, and Pedro poses need careful mapping into FTC field coordinates ([Mona Shores PR #150](https://github.com/Mona-Shores-FTC-Robotics/biobuzz/pull/150)).

Pedro 3 provides the hook to log from. Every `follower.update()` passes a `FollowerLog` to any `Consumer` registered through `withLogger(...)` ([Pedro Logging docs](https://pedropathing.com/docs/pathing/reference/logging)). Add the commanded throttles from `Intake` and `Intermediate`, and one log file per match would show exactly what auto did. Panels cannot show that, because its Capture plugin depends on the dashboard connection, which R704.D rules out during matches. These loggers add to Panels rather than replace it, since none of them can edit values live.

## Conclusion and next steps for 26507

The dashboard comparison turned out to matter less than it looked. Pedro's move to AutoTune removed Panels' main advantage of being installed by default, and R704.D took both dashboards out of matches, so for this team Panels now does one job: editing three classes' worth of static fields in the shop. That job is low-risk only if edits actually reach the robot, and the team's current build cannot guarantee that. The real lesson is that silent failure is the hazard. Panels' worst bugs this season produced no error, so the team's workflow needs a visible check. Pinning versions and freezing them before events matters more than which dashboard is installed.

The recommendation is to **keep Panels, upgrade to `com.bylazar:fullpanels:1.0.18`, verify it on the robot, and keep it out of event builds.** Do not switch to FTC Dashboard or the `com.bylazar.sloth` fork. Treat on-robot file logging as the season's real data upgrade, after the Q&A rules on it. What would change this advice: Panels breaking mid-season with no fix within about a week, or the Q&A ruling that installed-but-idle dashboards are illegal at events. Either would make FTC Dashboard (via Slothboard) or no dashboard at all the better option.
